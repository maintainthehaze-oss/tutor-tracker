# Roadmap §4.2 store size / save latency — 2026-10-11 (Claude Code, Opus 5.5)

Branch `store-speed` (worktree `../wt-store`), local only.

## Measured (real recovery file r093, locally, timings only; Node, memory adapter)
Envelope 12.65 MB: receipts 3.53 MB (working) + 3.46 MB (archive copy), archive rawSnapshot 4.26 MB,
everything else 1.40 MB. One save (settings.update) median ~510 ms. CPU profile: canonical text, JSON
clones and SHA-256 of the WHOLE envelope, several times per save; most of it is the immutable archive.

## Ruling (veto if wrong): two-way-door fix first, one-way split deferred
`repository.js` only, stored format unchanged:
- `freeze` records what it deep-froze; `canonical` caches the text of deep-frozen objects only.
- `cloneEnvelope` shares the deep-frozen archive instead of re-cloning it (draft, seal, publish,
  IndexedDB CAS, snapshot). The draft's archive is now read-only in memory, so an in-place archive
  edit by a command fails at once (tests updated; a whole-archive swap is still refused).
- `equal` short-circuits on the same reference.
Result: same commands through old and new code on the real envelope → integrity hashes and stored
envelope BYTE-IDENTICAL for 6 saves; reopen re-verifies; save median 510 → ~200 ms (2.3-2.5×).
Roadmap (b) "keep rawSnapshot out of the per-write hash" is effectively met (its text is computed once
per page load; still covered by the hash). Roadmap (a) receipts to their own IndexedDB store is NOT
done: it is the one-way envelope change; revisit only if saves still feel slow on the real device.
